Remote Worker Nodes

Add other machines to the app. A worker node lends its GPU or CPU to the same queue. A Plex database node does Plex-database work on the machine where Plex runs, which is the fix for Plex on Windows (#407). The main app stays in charge of everything. Nodes only do the work they're handed.

How it works, in five steps
  1. Run the node (Docker on Linux, or a small native install on Windows for the Plex database), then paste its address and key into the app's new Nodes page.
  2. The app checks the node: version, GPUs, and whether it can see your media at the paths you mapped. Problems show up in the node's own Setup Health.
  3. Add the node's GPU or CPU to a worker group, the same way as a local device. Schedules and job types work unchanged.
  4. When a node worker picks up a file, the app sends just the heavy FFmpeg step to it and gets small results back: frames, numbers or timestamps. The app writes every output itself.
  5. If a node can't see a file, drops out, or loses its GPU, the file goes to another worker and the node is flagged with a clear message.

2 · Who does what

Nodes are just workers. The app decides what runs, where, when and how often, and does every write.

The app

  • Holds the queue, schedules, worker groups and retries
  • Talks to Plex, Emby and Jellyfin, and holds every token
  • Checks a file before work: stat, ffprobe, Plex hash, "already done?"
  • Builds BIFs and trickplay from returned frames, and writes every output
  • Owns markers.db, the loudness state and the job logs
  • Stores each node's path mappings and settings
  • Watches node health and raises alerts

A worker node

  • Runs one step it's handed: frame extraction, a loudness pass, an audio fingerprint, the end-picture check, or credits detection
  • Maps the path, checks it's the same file, then runs FFmpeg on its own GPU or CPU
  • Reports progress, log lines and its own GPU/CPU fallbacks
  • Returns frames, numbers or timestamps, then deletes its temp files
  • Reports its GPUs, version and health when asked

A node never

  • Gets a Plex, Emby or Jellyfin token or URL
  • Writes outside its own temp folder (worker) or Plex's database (Plex database node)
  • Decides what to work on, or retries by itself
  • Sends back a path that the app then writes to
  • Opens a file outside its mapped folders

3 · Big picture

4 · Connecting and staying connected

Add a node by pasting its address and key, as with today's Plex helper. The node makes the key on first start and keeps it in its config folder, so a restart doesn't change it. The node also has a fixed ID, so the app notices if a different machine answers at the same address.

  • Health check: the app asks every node for its status every 30 seconds. While a node is offline the gap grows to at most 5 minutes, and a "Check now" button forces it.
  • While a file runs: the app's worker asks for progress every 1–2 seconds. Three failed asks in a row (about 12 seconds when tested) means the node is gone. The file goes back in the queue once.
  • Node restarts mid-file: its in-memory tasks are gone, so the app gets "unknown task" and puts the file back in the queue.
  • App restarts mid-file: the node stops any task the app hasn't asked about for 60 seconds, so nothing runs for nobody. The app's own job recovery then picks the file up again.
  • Same version on both sides: the node says its version and protocol. A mismatch shows "Update needed" and the node's workers stay idle. Watchtower usually fixes it within the hour.

5 · Path mappings, per node

Each node gets its own mapping rows, stored in the app: path on this app → path on the node. The app sends its own path with every task. The node translates it and checks that it's the same file before starting.

  • Same-file check: size and modified time to the nanosecond. Device and inode numbers are deliberately not compared, because they differ between machines even for the same file (measured: ZFS vs NFS vs Docker vs mergerfs).
  • Test access button: takes 3 real files from each library (from the server's library folders), runs them through both mappings, and checks them on the node. Results are per library, for example "Movies 3/3 ✓, TV Shows 0/3 ✗ not at /mnt/tv/…".
  • Suggestions: when a whole library fails, the node lists the top folders under its mount, so the editor can suggest the right prefix.
  • Plex database nodes need no media mapping. They work on Plex's database, not on media files.

6 · Worker groups with nodes

Groups don't change. A group member gains a node field. One group can mix local devices and devices from several nodes, and each device keeps its own budget.

  • The device picker lists "This app" devices first, then each node's devices labelled with the node name.
  • Schedules, job types and worker counts work per member, exactly as today. Loudness stays CPU-only, as today.
  • A node that is offline, out of date, key-refused or failing access gives its members zero capacity. The group shows the reason ("storage offline") and the "will this run" estimate counts it as zero.
  • Removing a node leaves its members visible with "node removed", so nothing disappears silently.

7 · GPU detection and monitoring

What a node reports

  • GPUs from the app's own detection code (took 0.7–1.3 s, JSON-safe)
  • FFmpeg version and hardware decoders
  • The credit-text GPU self-test result for each GPU
  • CPU cores, memory, free temp space, load
  • Busy slots, running tasks, version, uptime

How the app uses it

  • The Nodes page and the group device picker
  • "GPU lost" when a GPU disappears or stops passing its test decode
  • The existing per-GPU alerts ("keeps failing", "credits on CPU"), now with the node name
  • "Rescan GPUs" asks the node to detect again

Seen during testing: a host-level systemd reload made the running node container lose its NVIDIA GPU ("Failed to initialize NVML"), while new containers still saw it. So a node re-checks its GPUs every 5 minutes and after any GPU error. A lost GPU pauses that node's GPU members with "restart the node container" as the fix. CPU members keep working.

9 · When things go wrong

The node can't see the file

The mapping is wrong, the mount is stale, or a different copy is there. The node refuses in under a second, before FFmpeg starts.

The file goes to the next eligible worker, another node or a local device, never back to the same node. If every eligible worker can't see it, the file is marked failed: "not visible on storage, nuc".

After 3 different files fail on one node within 10 minutes, the node becomes Access problem. Its workers pause and an alert names the library and the path it tried.

Tested: wrong mapping, different file and path traversal were all refused, with reasons.

The node drops out mid-file

After 3 failed asks (about 12 seconds), the file goes back in the queue once and isn't counted. A second drop counts it as failed: "node unavailable twice".

Tested in a spike against the real dispatcher: one drop gave 3/3 succeeded and 0 failed; two drops gave exactly one failed row. 1,119 existing worker, dispatcher and parking tests passed.

The GPU fails on a file

The same rule as local workers: the node retries on its own CPU. The app never takes the work over itself.

The node loses its GPU

GPU members pause with "GPU lost: restart the node container". CPU members carry on.

Wrong version or wrong key

"Update needed" or "Key refused". The node's workers stay idle and the Nodes page says exactly what to change.

You cancel or pause the job

The app tells the node, and the node stops or freezes its own FFmpeg.

Tested: cancel stopped FFmpeg on the node in 0.63 s.

Worker hours close mid-file

As today, the running file finishes. If the node goes silent, the drop rule above ends the wait, so parking can't hang on a dead node.

10 · Logs

  • Job log: the node sends its log lines with each progress reply. The app's worker thread writes them into the job log as they arrive, prefixed with the node and device: storage/GPU0 · Extracting frames…. The worker writing them itself matters, because the job log only accepts lines from that thread.
  • Per-file results show the worker as "storage · GPU0", so it's always clear where a file ran.
  • Node log: each node keeps its own rolling log. The Nodes page has a "View log" button that reads it through the node API, so there's no SSH to the node.
  • FFmpeg failure files stay on the node. The app gets the summary and a pointer to the node log.

11 · Node Setup Health

This uses the same Must fix / Recommended / All good layout as server Setup Health, with current → recommended values.

Must fix

  • Can't reach the node
  • Key refused
  • Version differs from the app
  • A library isn't visible at the mapped path
  • A GPU used by a worker group is missing or failing
  • Plex database node: database not found, on a network drive, or not writable by this user

Recommended

  • Credit text falls back to the CPU on this GPU
  • Under 2 GB free in the node's temp folder
  • The node isn't in any worker group yet
  • Plex database node: Plex isn't running, so changes wait until it is

All good

  • Reachable, key accepted, same version
  • Every library visible, same files
  • GPUs pass their test decode
  • Plex database node: database on a local disk, open by Plex, writable

12 · Windows

The Plex database node on Windows, proven on a real Windows runner:

  • A live SQLite WAL connection locks exactly byte 128 of -shm, the same byte as on Linux. Checking it with a quick lock attempt tells "Plex has it open" from "nobody has it open".
  • That quick lock doesn't break Plex. A new connection opening during the lock just waited for it, with no error.
  • Restart Manager lists the processes holding the database open without taking any lock. It also lists our own process, which has to be filtered out. This is the safer check to use first.
  • Drive type: local disk = fixed (3); mapped drive and UNC path = remote (4). A subst drive reports fixed, the same as the disk underneath.
  • Today's helper code fails on Windows only at the Linux-only parts: fcntl, the mount check, user IDs and some signal names.
  • A self-contained build (PyInstaller, Flask + SQLite) is 25 MB and ran on a clean runner.
  • Install detail: a normal user can't create a logon task ("Access is denied"). So the node starts from the user's Startup entry instead, which needs no admin. The firewall rule needs one admin prompt, and only when the app runs on a different machine.

The app's own Plex database code on Windows: I ran the existing Plex database tests on the Windows runner with a small Windows layer (lock check, drive type, no fcntl). 874 passed, 39 failed, 6 skipped.

  • 23 failures are the tests, not the code. They fake Linux mount files to simulate NFS, Docker and so on, and the Windows layer doesn't read those fakes. They need Windows versions of the same cases.
  • 16 failures are real porting work. 2 are the SQLite address breaking on special characters in a Windows path. 14 are "item not found" in the marker write tests, most likely because Plex on Windows stores paths as D:\…. Both are in phase 3's scope.

Why no native Windows worker in the first version:

  • Windows needs a different GPU stack: d3d11va, QSV and AMF instead of VAAPI, and HDR tone-mapping through libplacebo or OpenCL.
  • The loudness FFmpeg is a patched Linux build, and pausing uses Linux signals.
  • Windows users with NVIDIA can run a worker node in Docker Desktop today. Intel and AMD GPUs on Windows would need the native worker, so it's a later phase, not a blocker.

14 · What I tested

A throwaway prototype node (the app image plus a small API) ran the app's real code against a real 22-minute 1080p HEVC episode. The "app" side had the media at /data and the node had it at /mnt/nas. Windows behaviour was tested on GitHub's Windows runner.

SAMEPreviews, CPU. 274 frames. Same JPEGs byte for byte, same BIF. 217.6 s on the app, 207.5 s on the node. Frames came back as one 3.8 MB file in 0.09 s.
SAMEPreviews, NVIDIA GPU (Quadro P5000). Same frames, same BIF. 52.5 s on the app, 45.8 s on the node. 4.5 MB back.
SAMELoudness. Same numbers (−23.00 LUFS and the rest), using the patched loudness FFmpeg inside the node.
SAMEIntro fingerprint (3,845 points, 15 KB) and end-picture frames (60). Identical on both sides.
SAMECredits, as one whole step. Same result on both sides. CPU 26.9 s vs 25.3 s, GPU 16.6 s vs 15.6 s. The node also passed back why credit text used the CPU ("Vulkan reports no hardware GPU"), so that message can still reach the job log.
PASSCancel. FFmpeg on the node stopped 0.63 s after cancel was pressed.
PASSWrong key refused (401). Access checks refused an unmapped path, a different file at the same path (size/time differ), a ../ escape, and a missing file. A task with a wrong mapping failed in 0.0 s, before any work started.
PASSSame file, seen through different mounts. Size and modified time matched on ZFS, NFS 4.2, a Docker bind mount and mergerfs. Device and inode numbers did not match, so the design compares size and time only.
PASSNode killed mid-file. The app called it unavailable after 12 s (3 failed asks). After a node restart, it no longer knew the old task, which is what tells the app to requeue.
PASSPut back in the queue, in the real job code (throwaway branch, not kept). One drop: 3 of 3 files still finished, 0 failed. Two drops on the same file: exactly one failed row. 1,119 existing worker, dispatcher and pause tests still passed.
PASSGPU detection on a node takes 0.7–1.3 s and its result travels fine as JSON.
FOUNDA node can lose its GPU while running. A host service reload made the running node say "Failed to initialize NVML". New containers were fine and a restart fixed it. That's why nodes re-check their GPUs every 5 minutes and after any GPU error, and why "GPU lost" is its own state.
PASSWindows (GitHub runner): the lock check, Restart Manager, drive types, the 25 MB build, and the logon-task check that ruled out a scheduled task (section 12). The Startup entry itself is checked in the beta.
FIXPrototype rough edges the real build must get right: cancel was reported as "failed" (must say cancelled), and an unknown task returned an error 500 (must be 404).

15 · How confident I am

High

Heavy steps on a node give the same result. Every step was run both ways on a real file and compared byte for byte. The app's existing functions run unchanged on the node.

High

Path mappings, file checks and the key. Every bad case I could think of was refused before work started, and size + time are stable across every mount type here.

High

Dropped node → back in the queue. Measured on a killed node, and the queue change was proved inside the real job code with the existing tests green.

High

Plex database node on Linux. It's today's Plex helper with two more calls, and the helper is already live.

Medium

Windows Plex database node. Locking, drive type and packaging are proven on a Windows runner. 16 real porting failures remain (Windows paths), and it hasn't touched a real Plex on Windows yet. That needs the beta with the #407 reporter.

Medium

Fitting nodes into worker groups and the dashboard. I know every place the code assumes a local device (about 12). It's careful work, not unknown work.

Medium

Docker Desktop on Windows reaching a native node (host.docker.internal). Not tested; checked during the beta.

Not v1

Native Windows worker for Intel/AMD GPUs. Possible later, but it's a separate FFmpeg and GPU build.

16 · Build order

  1. Node basics: node mode, key, API, health checks, the Nodes page, Add node and node Setup Health. No job runs on a node yet.
  2. Plex database node on Linux: today's Plex helper becomes this role, plus loudness writes and Library Health counts.
  3. Windows Plex database node: the Windows platform layer, the 25 MB build and the Startup install, then a beta with the #407 reporter.
  4. Executor seam in the app, local only: no change in behaviour, proved by the full test suite and markers_eval.
  5. Worker nodes for previews: path mappings, Test access, node devices in groups, putting files back in the queue, and the error rules in section 9.
  6. Worker nodes for loudness and markers.
  7. Docs and release. An architecture review runs on every phase above.

17 · What I need you to approve

Two node roles, one Nodes page, one way to connect. A node is a worker (does the heavy steps) or a Plex database node (opens Plex's database where Plex runs), or both. The Plex helper becomes the database role and existing helper setups carry over.
Nodes are grunt workers. The app keeps the queue, schedules, retries, tokens, mappings and every write. A node runs one step and sends back frames, numbers or timestamps.
The app calls the node, with a key the node makes. Both must run the same version; otherwise the node sits idle and says "Update needed".
Path mappings live in the app, per node. Checked with size + modified time, and tested per library when you add the node.
A dropped node puts its file back in the queue once. A second drop on the same file marks it failed.
"Can't see the file" tries the next worker. Three different files missing within 10 minutes marks the node "Access problem" and pauses it.
A GPU problem falls back to the node's own CPU, never to the app's.
The Plex database node comes first (Linux, then Windows for #407), before worker nodes.
Windows ships as a self-contained build started from the user's Startup entry, running as Plex's user. No Python, no admin except one firewall prompt.
No native Windows worker in v1. Windows + NVIDIA users can run a worker node in Docker Desktop.
