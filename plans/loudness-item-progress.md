# Loudness worker card moves: per-stream ffmpeg progress reaches the worker's progress bar
Status: done (local commit on feat/loudness-item-progress; no PR until the user approves)
Issue: diblaze/media_preview_generator#5
Base: upstream/dev d70bcbe. Cited lines are upstream/dev; `jobs/`, `web/` and tests are identical in the working tree.

## Goal
While a loudness item runs, its worker card shows a moving percent (streams done plus the running stream's fraction from ffmpeg's `-progress` output) and ffmpeg's speed, so a single-file webhook job's bar leaves 0% before the file is done, with the loudnorm command, report parsing, pause, cancel and timeout unchanged.

## Deferred (YAGNI)
- A separate job-level progress change (`processed_items` counting whole files) — not needed: E6 already folds the worker percent into the job percent once it is nonzero; reopen only if the job bar still sits at 0% after this lands.
- Duplicate loudness jobs per file from Sonarr plus Plex webhooks (observed: 4 jobs for Lanterns S01E08) — separate issue candidate; reopen as its own plan.
- Remaining-time (ETA) for loudness from `speed` and the stream length (`remaining_time=` in E4) — reopen if the hidden ETA chip is missed; one extra expression in `report`.
- Keeping the "Loudness n/N" phase text visible after `ffmpeg_started` (app.js:3085 hides it in favour of the percent) — reopen if users want the stream counter; it is a UI change for all kinds.
- Weighting streams by their own `duration_ms` instead of equally — reopen if a file with very unequal stream lengths shows a jumping bar.

## Open questions
- Should `report(0.0, "0.0x")` at stream start be kept (bar appears at once, phase text disappears) or should the bar wait for ffmpeg's first progress block (up to 0.5 s of "Loudness 1/2" first)? Default: keep it; it mirrors previews (E4) and makes a 1-stream file leave "Working…" immediately.
